# Architecture decisions

Short ADRs. Each records a decision that was not obvious, the alternative that
was rejected, and the cost that was accepted. This file is part of the
portfolio: the reasoning is the point, not the conclusion.

Format: **Context → Decision → Alternative rejected → Cost accepted.**

---

## ADR-001 — SQLite locally, PostgreSQL-shaped schema

**Context.** The system is local-first and single-user. It may eventually need
to run somewhere shared, and the schema is meant to be shown as an example of
work that would survive contact with a real environment.

**Decision.** SQLite as the default engine, but no SQLite-specific construct
anywhere in the schema. `Numeric` for money, `Date`/`DateTime` for time,
`VARCHAR` + `CHECK` for enumerations, explicit `ON DELETE` behaviour on every
foreign key. Moving to Postgres is a change to `TOS_DATABASE_URL` and nothing
else. `backend/tests/test_portability.py` compiles every table against the
Postgres dialect so the claim is checked rather than asserted.

**Alternative rejected.** Postgres in Docker from day one. It removes the
constraint entirely, but it also means the application cannot start without a
running container, which contradicts local-first, and it removes the discipline
that keeps the schema portable — which is itself the transferable lesson.

**Cost accepted.** SQLite does not enforce foreign keys without a per-connection
pragma, has no native decimal type, and cannot `ALTER` a column. All three are
handled (pragma in `db.py` and `alembic/env.py`, `Numeric` converted by
SQLAlchemy, `render_as_batch=True` in Alembic), but each is a place where a
careless change would break quietly.

## ADR-002 — Enumerations as `VARCHAR` + `CHECK`, lookup tables where the set grows

**Context.** The schema has two kinds of closed value set: those that only
change when the code changes (`status`, `severity`, `persona`, `kind`), and
those the user will extend (deliverable types, skill domains, review criteria).

**Decision.** The first kind are `VARCHAR` columns with a named `CHECK`
constraint, generated by `enum_check()` in `models/base.py`. The second kind
are lookup tables with a `code` column.

**Alternative rejected.** Native `ENUM` types. They do not exist in SQLite, and
in Postgres adding a value to one is a migration — so a new deliverable type in
2032 would mean a schema change rather than an insert.

**Cost accepted.** `CHECK` constraints are string comparisons, so a typo in
application code fails at write time rather than at import time. Mitigated by
defining every value set once in `models/base.py` and importing it.

## ADR-003 — A `profile` table in a single-user application

**Context.** The application must be demonstrable in an interview or a
conference without exposing real career data, and the demo must exercise the
real schema rather than a parallel fixture that drifts from it.

**Decision.** Every row of user data carries `profile_id`, and `profile.is_demo`
separates the shipped demonstration dataset from the owner's real one. Both live
in the same database, against the same constraints. `seed_demo` is destructive
within the demo profile and touches nothing else.

**Alternative rejected.** A separate demo database, or a sanitising export
script. Both drift: the moment the schema changes, the demo path is the one
nobody tests, and it breaks in front of an audience.

**Cost accepted.** Every query in the application must filter on profile. This
is a real ongoing tax, paid on purpose — and it is the same tax multi-tenancy
imposes, which makes it worth practising.

## ADR-004 — Acyclicity enforced in the service layer, not the schema

**Context.** The skill graph must be a DAG. A cycle makes the critical path,
the learning order and blocked-skill detection all meaningless.

**Decision.** A `CHECK` constraint rules out self-loops, which is the only cycle
a constraint can catch cheaply. Longer cycles are detected by an iterative
depth-first search in `services/graph.py`, run before any edge is written by the
seed loader and before any edge is created through the API. The taxonomy is
rejected wholesale rather than partially loaded.

**Alternative rejected.** A recursive CTE trigger. Beyond being non-portable, a
recursive CTE over a cyclic graph does not report the cycle — it runs until it
hits a row limit. Naming the nodes involved requires a traversal that remembers
its own stack, which is exactly what the Python implementation does.

**Cost accepted.** The invariant lives outside the database, so a direct `INSERT`
into `skill_edge` could create a cycle. Accepted because the only writers are the
seed loader and the API, and because `tos graph check` detects it in under a
second on a graph this size.

## ADR-005 — Graph logic as pure functions over edge pairs

**Context.** Graph traversal is the part of this system most likely to be
subtly wrong: a cycle detector that mistakes a diamond for a cycle, or a
critical-path ranking that counts already-satisfied dependents.

**Decision.** `services/graph.py` takes `list[tuple[node, node]]` and returns
plain Python. No session, no models, no database. The database layer maps rows
to pairs and back.

**Alternative rejected.** Methods on the `Skill` model, or a `networkx`
dependency. Model methods make every graph test require a database and a
seeded taxonomy — where a wrong answer looks plausible. `networkx` is a large
dependency for six functions, and implementing them is a stated learning goal.

**Cost accepted.** One mapping step between rows and pairs, and re-derivation
of adjacency on each call. Both are irrelevant at 83 nodes; if the taxonomy
ever reaches thousands, the adjacency map gets built once and passed in.

## ADR-006 — Every monetary figure references an `assumption`

**Context.** The Business Case Lab exists to train the reasoning that survives
a hostile review board. Its value is not in storing numbers but in making their
provenance inescapable.

**Decision.** `roi_line.amount_assumption_id` is `NOT NULL`. A leaf of the cause
tree has no value column at all — it is the product of its `cause_driver` rows.
A fixed, perfectly known cost is expressed as an assumption whose low, base and
high values are equal.

**Alternative rejected.** A nullable `amount` column alongside the assumption
reference, for "simple" lines. It would be used for every line under time
pressure, and the ROI model would quietly revert to a spreadsheet with extra
steps. More importantly, sensitivity analysis needs something to vary: an
amount typed directly has no range, so it cannot appear in a tornado chart, and
the fragile assumptions would be exactly the ones excluded from the analysis.

**Cost accepted.** Data entry is slower than a spreadsheet, and a trivial cost
line costs two rows. This is the intended friction.

## ADR-007 — Scenarios as a rule, not as stored numbers

**Context.** The pessimistic, base and optimistic cases must stay consistent
with each other as a model is edited.

**Decision.** Ranges live on the assumption (`low_value`, `base_value`,
`high_value`). A scenario is a *rule* for choosing within the range, applied at
computation time: the pessimistic case takes the unfavourable end given whether
the line is a cost or a benefit — high for costs, low for benefits.

**Alternative rejected.** Three stored amounts per line, one per scenario. They
drift. An assumption revised in the base case but not in the other two produces
a model that is internally inconsistent in a way nothing detects, and the
inconsistency surfaces in front of the audience.

**Cost accepted.** Cannot express a scenario that is not a monotone function of
the assumption ranges — for instance "in the pessimistic case the project is
also six months late". Scenario-specific structure will need a modelling
extension in Phase 2 if it proves necessary; it is not free-form today.

## ADR-008 — No derived values in the normalised layer

**Context.** Branch totals, NPV, payback, quota compliance and skill rankings
are all wanted in the interface, and all are expensive-ish to compute.

**Decision.** None of them is stored in the normalised schema. They are computed
from base rows on read, and materialised only into the star layer in Phase 4,
where staleness is expected and the rebuild is explicit.

**Alternative rejected.** Cached totals on `cause_node` and `roi_model`,
maintained by triggers or service code. Every such cache is a second source of
truth that eventually disagrees with the first, usually after an edit path
nobody remembered to hook.

**Cost accepted.** Reads recompute. At the scale of one person's career — tens
of business cases, hundreds of deliverables — this is not measurable. There are
two deliberate exceptions, both documented in the models: `case_review.overall_score`,
because it is the agent's verdict under the rubric weights in force at the time
rather than a recomputable aggregate, and `skill_state.last_practised_on`,
denormalised from evidence to keep the decay query cheap and marked as
service-maintained.

## ADR-009 — One `agent_run` table, prompts in hashed `.md` files

**Context.** Three agents (posting extraction, review board, periodic review)
all call the same API and all produce output that is stored and read back
months or years later.

**Decision.** One `agent_run` row per call, referenced by whatever the call
produced. Prompts live in versioned `.md` files outside the Python source, and
`agent_run.prompt_sha256` records the hash of the file actually used.

**Alternative rejected.** A separate `extraction_run` table per agent, and
prompts as Python string constants. Separate tables triplicate the same columns.
Prompts in Python make a prompt change indistinguishable from a code change in
review, and make it impossible to tell whether the file on disk today is the
one that produced a score in 2027 — the hash makes that verifiable.

**Cost accepted.** A nullable foreign key on each consuming table, and prompt
loading becomes file I/O that needs its own error path.

## ADR-010 — Star schema built by versioned SQL, outside Alembic

**Context.** The analytical layer (`fact_activity`, `fact_case_review`,
`dim_skill`, `dim_date`) is both a feature — it feeds Power BI — and a
deliberate exercise in dimensional modelling.

**Decision.** Fact and dimension tables are created and rebuilt by numbered SQL
files in `sql/transformations/`, executed by a Python job. `alembic/env.py`
excludes any table named `fact_*` or `dim_*` from autogeneration.

**Alternative rejected.** Managing the star schema in Alembic alongside the
normalised tables. Alembic would then propose drops for tables the job creates,
on every autogenerate. More to the point, hand-written, commented, readable SQL
is the artefact worth having here — it is the part of this repository closest
to what the target roles actually require.

**Cost accepted.** Two mechanisms create tables in one database, and the split
must be understood before either is changed. The naming prefix makes the
boundary mechanical rather than a matter of memory.

## ADR-011 — Documentation in English, French where it is read rather than shown

**Context.** The owner works in French. The stated goal is international
reputation by 2032, and this repository is intended to be shown to recruiters,
conference audiences and clients.

**Decision.** Code, schema, API, seed data and these documents in English.
Skill codes in English specifically, because job postings — the input to the
Gap Radar — are predominantly English, and normalising a French taxonomy
against English postings would add a translation step to every extraction.

**Alternative rejected.** French throughout. More comfortable day to day, but it
makes the strongest artefact in the portfolio unreadable to a large part of its
intended audience.

**Cost accepted.** A small ongoing translation tax for the owner, and interface
labels that may want a French layer in Phase 1. That layer is cheap to add and
does not touch the schema.

## Deliberately not built

Each of these was considered and left out. Listing them is part of the
argument: an architecture is defined as much by what it refuses.

- **Microservices.** One person, one database, one deployment. Splitting this
  would add network calls between functions that share a transaction.
- **Kafka or any broker.** Nothing here is a stream. The highest-frequency
  event in this system is "a deliverable was published", which happens a few
  times a quarter.
- **Kubernetes.** A single container with a mounted volume.
- **A background worker.** Agent calls take seconds and are user-initiated. If
  batch extraction of dozens of postings ever becomes real, this changes — and
  it changes to a task table polled by the CLI, not to Celery and Redis.
- **An ORM-managed analytical layer.** The SQL is the deliverable.
- **`localStorage` or front-end state as a source of truth.** The API is the
  only writer; the front end renders and posts.
- **Gamification.** No badges, streaks or points. The quarterly review says
  what shipped and what did not, in plain language, and says nothing when
  nothing shipped except that nothing shipped.
